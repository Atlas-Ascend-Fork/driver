# 模块文档生成 skill

通用模块 md 文档生成 skill。采用**三层递进架构设计模板**（模块定位→逻辑视图→子模块细化），配合 per-module `knowledge.md` 获取模块特有信息（源码范围、子模块清单、API 域、参考文档索引等）。

## 必需参数

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| project_root | string | 是 | 项目根目录绝对路径 |
| output_dir | string | 否 | 文档输出目录(默认{project_root}/.reverse_analysis/output/{module}/{ver}/) |
| model_id | string | 否 | 大模型名称(主动向模型询问获取) |
| depth | string | 否 | shallow/standard/deep(默认deep) |
| language | string | 否 | zh(默认)/en |
| reference_docs_dir | string | 否 | 参考文档目录(默认{project_root}/../docs/modules/{module}/ 或用户指定) |
| analysis_data_dir | string | 否 | 预扫描JSON目录(如存在则读取加速，默认{project_root}/.reverse_analysis/data/) |
| knowledge_md | string | 否 | knowledge.md 路径(默认{output_dir}/knowledge.md) |

## 模块源码范围（从 knowledge.md 加载）

> 源码范围、子模块清单、API 说明均从 `knowledge.md` 加载，不在 skill 中内嵌。
> knowledge.md 的生成流程见 `references/knowledge-template.md` 的 CK0_KNOWLEDGE 步骤。

- **源码范围**：读 knowledge.md §2（HAL 路径 + SDK 路径）
- **子模块清单**：读 knowledge.md §3（HAL 子目录 + SDK 子目录，按功能域/阶段分组）
- **API 说明**：读 knowledge.md §4（API 域划分 + 函数列表）
- **参考文档索引**：读 knowledge.md §6（如有）

## 执行协议（完整CK0-CK10，保留）

**核心原则**：不得因上下文限制简化任何执行步骤。

### 步骤0：知识加载 [CK0_KNOWLEDGE]

**此步骤是模块知识加载的前置——必须在 CK1_INIT 之前完成。**

1. 检测 `{knowledge_md}` 是否存在
   - 存在且有效 → 加载 knowledge.md，进入 CK1_INIT
   - 不存在 → 进入引导生成流程（3 轮交互），详见 `references/knowledge-template.md`
2. 引导生成流程完成后，knowledge.md 保存到 `{output_dir}/knowledge.md`
3. 输出 `[CK0_KNOWLEDGE LOADED]` + knowledge.md 路径

### 严禁伪造（CRITICAL — 保留source-code-analysis Rule 7）

**核心原则：参考文档是辅助理解，源码是唯一验证标准。**

> **绝对禁止**：用参考文档内容替代源码验证。参考文档（reference_docs_dir 下的 .md）用于**辅助理解**模块功能和架构，但文档中的**所有技术声明**（函数名、行号、结构体字段、文件路径、算法逻辑）**必须从实际源码中 Grep/Read 确认**后才能写入。
>
> **禁止 `[待结合代码验证]`**：文档中不允许出现 `[待结合代码验证]` 标注。每个函数引用必须有 `file:line`（如 `gen_allocator.c:438`），每个结构体必须有源码行号（如 `// mga.c:25`）。如果无法从源码验证，标注 `[未验证]` 并说明原因，但**不得用参考文档内容伪装为已验证**。

1. 禁止猜测函数名命名模式（HAL `drv*` ≠ 内核 `*_core`）
2. 禁止估算行号（必须 Read 确认）
3. 禁止简化数据结构字段
4. 禁止用HAL前缀替代内核前缀
5. 禁止推断文件名
6. 禁止猜测ioctl分发机制
7. 未验证声明必须标注`[未验证]`（**不是** `[待结合代码验证]`）
8. **禁止先生成后验证**：必须先完成 CK1V_SCAN 四层验证（Level 1-4）再写文档。**禁止**在四层验证未完成时批量生成 design.md（如 Python 正则提取函数名后直接写文档）。典型错误：v1 批量生成 12 个文件时只做了 Level 1（Grep 确认存在），Level 2-4 全部跳过，导致 54 个 FAIL。正确顺序：先更新 skill 规则 → 再分发 sub-agent 逐个生成（每个 sub-agent 独立做 Level 1-4）→ 主 agent 收集结果 + CK10 反向刷新。

### 步骤1：初始化 [CK1_INIT]

1. 解析路径：project_root、output_dir(默认基于knowledge.md §1的{module}/{ver})、reference_docs_dir
2. 加载 knowledge.md 获取源码范围（§2）和子模块清单（§3）
3. 读取参考文档索引（knowledge.md §6 可用时）
4. 读取 module_map.json（如存在，筛 knowledge.md §2 指定路径）
5. 读取README（knowledge.md §2 HAL 路径下的 README.md，如存在）
6. 收集Git信息：`git rev-parse --short HEAD` / `git branch --show-current` / `git log -1 --format=%ai`
7. 获取model_id（向模型询问"你的模型名称是什么"）

### 步骤1.5：源码扫描验证 [CK1V_SCAN]

**此步骤是文档质量的关键——必须对每个要写入文档的函数/结构体/标志进行源码验证。**

**验证四层框架**（每个声称必须达到对应层级，不可用低层级替代高层级）：

| 层级 | 验证内容 | 方法 | 对应步骤 | 典型错误 |
|------|---------|------|---------|---------|
| Level 1: 存在性 | 函数/结构体在源码中存在，行号正确 | Grep | 步骤 1-7 | 编造函数名/行号 |
| Level 2: 签名正确性 | 参数类型、返回类型、参数个数准确 | Read 函数声明行 | 步骤 2-4 | 正则提取漏掉 `enum`/`void *` |
| Level 3: 实现正确性 | 数据结构、算法、dispatch 逻辑、支持/不支持 | Read 函数体 | **步骤 10** | 声称用红黑树实际用链表 |
| Level 4: 语义正确性 | 参数的中文描述与调用者代码一致 | Read 调用者上下文 | 步骤 9 | 参数方向描述反了 |

> **CRITICAL：Level 1 通过不代表 Level 2-4 通过。函数存在于正确行号（Level 1），不代表签名正确（Level 2），不代表数据结构描述正确（Level 3），不代表参数语义正确（Level 4）。每层必须独立验证。**

1. Glob `{hal_src_dir}/**/*.{c,h}` 和 `{sdk_src_dir}/**/*.{c,h}` 确认源码文件存在（路径从 knowledge.md §2 获取）
2. **Grep 每个对外接口函数名**：确认函数在源码中存在，获取行号（如 `func_name : file.c:438`）
3. **Grep 每个内部关键函数名**：确认核心算法函数存在（如 `mga_alloc`/`mga_expand`/`mga_shrink`）
4. **Read 结构体定义**：Read 包含结构体的源码文件，确认字段名、类型、注释完整（如 `struct ga_inst` → Read gen_allocator.c:49-56）
5. **Grep 宏/标志定义**：确认 flag/枚举定义在源码头文件中（如 `MODULE_FLAG_XXX` → module.h:44）
6. **统计文件行数**：每个源码文件的行数，写入 §5 子模块概述
7. **验证参考文档与源码一致性**：如果参考文档中的函数名/结构体与源码不一致，**以源码为准**，在文档中使用源码中的实际名称
8. **调用者分析（CRITICAL — 依赖关系完整性保障）**：对子模块的每个对外接口，在**整个模块代码库**（不仅是子模块自身目录）中 Grep 搜索调用者，确保 §3.2 被依赖关系完整：
   - 搜索范围：`{hal_src_dir}` + `{sdk_src_dir}`（从 knowledge.md §2 获取，跨目录搜索）
   - 搜索方式：Grep 接口函数名（如 `pmm_for_each_seg`），找出所有调用文件和行号
   - 搜索目的：发现参考文档未列出的调用者（如参考文档只列了 mpl/smm 调用 pmm，但 Grep 发现 pmq 也调用了 `pmm_for_each_seg`）
   - **禁止只读子模块自身源码**：子模块的接口调用者可能在其他目录
   - **禁止只依赖参考文档列出的依赖**：参考文档可能遗漏调用者，必须用 Grep 验证完整性
   - 结果写入 §3.2 被依赖关系简表（接口函数 \| 主要调用者 \| 用途），多个调用者用 `/` 分隔合并到一行，不列调用位置
9. **语义验证（CRITICAL — 防止"行号对了但理解错了"）**：对每个对外接口函数，至少读取 **2 个调用者**的上下文代码（调用点前后各 5 行），验证参数的实际传入值与文档中的中文描述一致：
   - **验证内容**：
     - 读取调用者代码，确认每个参数实际传入了什么值（如 `user_devid` 实际传入的是 HOST 还是 DEVICE）
     - 对照文档中对该参数的中文描述，确认描述与调用者代码一致
     - 如果多个调用者传入不同值，需要在文档中说明不同场景下的参数含义
   - **常见语义陷阱**（必须规避）：

     | 陷阱类型 | 示例 | 错误原因 |
     |---------|------|---------|
      | **函数名误导** | `register_to_master` 字面看像"注册到master"，但实际 master 是 `user_devid`（本端），不是 `devid`（对端） | 从函数名推断参数语义，而非从调用者代码 |
      | **类型名误导** | 参数类型 `struct dst_va`（destination VA），"destination"让人以为 `devid` 是目标端，但实际 `devid` 是内存拥有方（源端/对端） | 从类型名推断参数语义 |
      | **方向性描述错误** | 将源端参数描述为"被注册到的目标设备"，实际是"内存拥有方" | 没有读调用者验证方向 |

   - **验证方法**：对调用者代码中的 `dst_va_pack(devid, ...)` 或类似函数，追踪 `devid` 的来源（如 `get_host_devid()` 返回 HOST），确认参数实际语义
   - **禁止**：
      - 从函数名推断参数语义（函数名可能有历史遗留或抽象层命名）
      - 从参数类型名推断参数语义（类型名可能从不同视角命名）
      - 只读函数签名不读调用者代码就写参数描述
   - **结果**：在文档接口表中，每个参数的中文描述必须有调用者代码佐证
10. **实现验证（CRITICAL — 防止"签名对了但实现描述错了"）**：对文档中每个**数据结构/算法/dispatch 逻辑/支持范围**的描述，必须 Read 对应的函数实现源码验证：
    - **验证内容**：
      2. **数据结构声称**：声称"用红黑树"→ Read init 函数确认是 `rbtree_init` 还是 `INIT_LIST_HEAD`；声称"用链表"→ Read init 函数确认是 `INIT_LIST_HEAD` 还是 `rbtree_init`
      3. **dispatch 逻辑声称**：声称"根据 overlap_type 分发"→ Read 函数体的 if/else 分支确认每种类型的处理
      4. **支持/不支持声称**：声称"仅支持 NON_OVERLAP"→ Read 函数体确认其他类型返回 NULL/Error
      5. **特殊行为声称**：声称"OVERLAP 返回 INVALID"→ Read 函数体确认该返回值
    - **禁止泛化（最危险的认知偏差）**：

      | 泛化类型 | 示例 | 错误原因 |
      |---------|------|---------|
      | **从单一样本推广到全部** | 读了 NON_OVERLAP 用 `rbtree_init` → 推广"三种类型均用红黑树" | OVERLAP 实际用 `INIT_LIST_HEAD`（链表），没读 OVERLAP 的 init |
      | **从 union 字段名推断实际使用** | union 有 `rbtree_root root` 和 `list_head head` → 推断都用 `root` | `head` 的 `/* reserve */` 意为"预留给链表实现"，不是"未用" |
      | **从注释推断行为** | `/* reserve */` → 推断"未用" | 实际意为"预留给特定实现使用" |

    - **验证方法**：
      - 对每种类型/变体，**独立 Read 其 init 函数**，确认实际使用的数据结构
      - 对每个 dispatch 函数，**Read 函数体的 if/else 分支**，确认每种类型的实际处理
      - 对每个"不支持"声称，**Read 函数体确认返回值**（NULL/Error/直接 return）
    - **结果**：在文档中，每个数据结构/dispatch/支持范围描述必须有函数体源码行号佐证
11. 输出 `[CK1V_SCAN PASSED]` + 验证结果表（函数名|文件:行号|调用者列表|参数语义验证结论|实现验证结论）

> **禁止跳过此步骤**。不执行 CK1V_SCAN 直接写文档 → 视为违规，必须重新执行。
> **核心禁止条款**：

> - 禁止用参考文档替代源码验证（函数名可能有差异）
> - 禁止只读子模块自身源码不做调用者分析（调用者可能在其他目录）
> - 禁止只验证行号不验证语义（签名正确不代表参数描述正确）
> - 禁止从单一类型泛化到所有类型（每种类型/变体必须独立 Read 验证）
> - 禁止从字段名/注释推断实际使用（`/* reserve */` ≠ "未用"）
> - 禁止用正则提取替代 Read 函数声明行（正则可能漏 `enum`/`void *`）
> - 禁止先生成后验证（必须先完成四层验证再写文档）
> - 禁止从截断的 sub-agent 输出写文档（必须 Read 完整输出文件）
> - 禁止从推断而非提取数据写文档（必须引用 sub-agent 的提取结果）
> - 禁止 edit 后不验证残留（修正后必须 Read 相邻 ±10 行确认无残留）
> - 禁止只改图不改文或反之（Mermaid 图与文字流程必须一致）

确认生成模块设计文档（三层递进结构）。用户直接请求→确认；Agent调度→自动确认。

### 步骤4：模块文档生成 [CK4_MODULE]（核心——三层递进模板）

**生成流程（严格按顺序执行，不可跳过）**：

1. **Read 参考文档**（辅助理解）：Read knowledge.md §6 指定的参考文档（如有），理解功能概述、架构关系、设计要点
2. **Read 源码**（主验证）：Read 实际 .c/.h 源码文件，验证参考文档中的每个声明：
   - Grep 函数名 → 确认存在 + 获取行号
   - Read 结构体定义 → 确认字段完整
   - Read 函数实现 → 确认算法逻辑
   - Grep 宏/标志 → 确认定义位置
3. **Write 文档**：基于源码验证结果（非参考文档内容）写入文档，所有函数标注 `file:line`，所有结构体标注 `// file:line`
4. **如果源码验证发现参考文档有误**：以源码为准，使用源码中的实际函数名/结构体名/行号

> **参考文档 vs 源码**：参考文档提供"这个模块做什么"的理解框架，源码提供"具体怎么做"的验证事实。文档中的每个技术声明必须追溯到源码 file:line，不能追溯到参考文档。
>
> **禁止**：只读参考文档不读源码就写文档。**禁止**：用参考文档的函数名/行号替代源码验证。

**按三层递进结构生成文档**，输出到 `{output_dir}/README_{model_id}_{YYYYMMDD}.md`：

**三层骨架详见 `references/three-layer-template.md`。** 各节具体内容根据 knowledge.md §3 子模块清单推导，不内嵌任何模块特有内容。

### 步骤8：完整性检查 [CK8_CHECK]

**此步骤是文档质量的最终保障——必须逐项验证，不通过不得输出 `[CK8_CHECK PASSED]`。**

**完整性清单**（三层递进）：

- [ ] 第一层完整：软件栈位置+主要功能特性+周边依赖
- [ ] 第二层完整：子模块划分+协作架构(含Mermaid图)+设计机制
- [ ] 第三层完整：各功能域子模块细化（根据 knowledge.md §3 子模块清单）
- [ ] Mermaid图≥3（协作架构图+时序图+依赖图）
- [ ] 行数≥knowledge.md §7 指定下限

**伪造检查清单**（11项，逐项执行）：

- [ ] **函数名验证**: 所有引用的函数名是否在源码中 Grep 确认存在？函数名是否与源码**实际名称**一致（非参考文档名称）？
- [ ] **行号验证**: 所有行号引用是否从源码中 Read 确认（偏差≤5）？**禁止**用参考文档的行号。
- [ ] **签名验证**（Level 2 — CK1V_SCAN 步骤2-4）: 所有函数签名的**参数类型、返回类型、参数个数**是否从源码 Read 函数声明行确认？**禁止**用 Python 正则提取替代 Read（正则可能漏 `enum`/`void *`）。
- [ ] **数据结构验证**: 所有结构体字段是否从源码 Read 确认完整+类型正确？
- [ ] **ioctl命令验证**: 所有ioctl命令名是否从对应 ioctl 头文件 Grep 确认？
- [ ] **文件路径验证**: 所有引用的文件路径是否通过 Glob 确认存在？
- [ ] **源码验证声明**: 文档元信息"源码验证声明"是否记录了已验证文件列表？
- [ ] **参数语义验证**（Level 4 — CK1V_SCAN 步骤9）: 每个对外接口函数的参数中文描述是否通过读取调用者代码验证？是否存在从函数名/类型名推断语义的情况？**禁止**只读函数签名不读调用者代码就写参数描述。
- [ ] **实现验证**（Level 3 — CK1V_SCAN 步骤10）: 文档中每个**数据结构/dispatch 逻辑/支持范围/特殊行为**的描述是否通过 Read 函数体验证？是否存在从单一类型泛化到所有类型的情况？是否存在从字段名/注释推断实际使用的情况？**禁止**不读 init 函数就声称数据结构类型。
- [ ] **图文一致性验证**: Mermaid 图中的调用者/接口/数据流描述与图下方文字流程描述是否一致？**禁止**只改图不改文、或只改文不改图。修正图后必须同步检查相邻文字流程，修正文字后必须同步检查相邻 Mermaid 图。
- [ ] **修正残留检查**: 每次使用 edit 工具修正后，必须重新 Read 修正区域及相邻 ±10 行，确认 oldString 范围外的旧行没有被残留。**禁止** oldString 只覆盖部分需替换的行而留下尾部残留。

**`[待结合代码验证]` 检查（CRITICAL）**：

- [ ] 文档中**不允许出现** `[待结合代码验证]` 标注
- [ ] 每个函数引用必须有 `file:line`（如 `gen_allocator.c:438`）
- [ ] 每个结构体必须有源码行号注释（如 `// gen_allocator.c:49`）
- [ ] 如果有 `[待结合代码验证]`：**CK8_CHECK FAIL**，必须补充源码验证后重新检查
- [ ] 仅允许 `[未验证]`（源码中确实找不到，如内联函数/宏定义）和 `[文件存在,行数待验证]`（文件确认存在但行数未统计）

> **CK8_CHECK FAIL 处理**：如果有 `[待结合代码验证]`，必须回到 CK1V_SCAN 步骤，Grep/Read 源码补全验证，替换为真实 `file:line`，然后重新执行 CK8_CHECK。如果参数语义验证不通过（Level 4），必须回到 CK1V_SCAN 步骤9，读取调用者上下文代码，修正参数描述。如果实现验证不通过（Level 3），必须回到 CK1V_SCAN 步骤10，Read 函数体源码，修正数据结构/dispatch/支持范围描述。如果签名验证不通过（Level 2），必须 Read 实际函数声明行，修正参数类型/返回类型。如果有 edit 残留或图文不一致，必须重新 Read 修正区域及相邻 ±10 行，扩大 oldString 范围覆盖所有需替换的行，同步修正图和文字。**不得**跳过伪造检查直接输出文档。

### 步骤10：反向刷新 [CK10_REVERSE_REFRESH]

**触发条件**：某层级的所有子模块 design.md 完成 CK1V_SCAN 四层验证（Level 1-4）后。

**问题背景**：上层级文档（如 share_design.md）在子模块之前生成，其子模块概述部分可能包含 Level 1 阶段的推断性描述。子模块深度验证（Level 2-4）后发现的修正（如数据结构纠正、参数语义纠正、签名纠正）**不会自动传播到上层级文档**。CK10 解决这个传播缺失。

**执行流程**：

1. **识别上层级文档**：读取当前层级的 design.md（如 `4_share/share_design.md`），定位其中的子模块概述章节（如 §1 子模块清单表、§5 子模块概述表）
2. **对每个子模块**，对比上层概述 vs 子模块验证结论：
    - Read 上层级文档中该子模块的概述条目（数据结构/参数语义/函数签名/支持范围/dispatch 逻辑）
    - Read 子模块 design.md 中对应条目的验证结论（changelog 中标注的 v{N}/v{N+1} 修正项）
    - 对比一致性：

     | 对比项 | 上层级可能过时的描述 | 子模块验证后的正确结论 |
     |--------|-------------------|---------------------|
     | 数据结构 | "红黑树"（Level 1 推断） | "链表"（Level 3 验证） |
     | 参数语义 | "目标设备"（Level 1 推断） | "源端设备"（Level 4 验证） |
     | 函数签名 | `void func(u64 flag)` | `void *func(enum type, u64 flag)`（Level 2 验证） |
     | 支持范围 | "全类型支持" | "仅 NON_OVERLAP 支持"（Level 3 验证） |

3. **不一致时**，以子模块验证结论为准，修正上层级文档：
   - 用子模块 design.md 中的验证结论替换上层级概述条目
   - 保留上层级文档原有的引用格式和结构
   - 在修正处标注来源：`(反向刷新: 来自 {submodule}_design.md v{N} Level {X} 验证)`
4. **更新上层级 changelog**：

```text

   | v{N+1} | {date} | CK10_REVERSE_REFRESH: 根据 {N} 个子模块的 Level 2-4 验证结论修正 {M} 处概述条目（来源: {submodule}_design.md v{N} 数据结构修正 / {submodule2}_design.md v{N-1} 参数语义修正 / ...） |

   ```

5. 输出 `[CK10_REVERSE_REFRESH PASSED]` + 修正结果表（子模块名 | 对比项 | 上层旧值 | 子模块正确值 | 是否修正）

**反向刷新范围**：

| 上层级文档 | 子模块概述位置 | 反向刷新内容 |
|-----------|--------------|-------------|
| `4_share/share_design.md` | §1 子模块清单、§5 子模块概述 | 数据结构/参数语义/签名/支持范围 |
| 根 `design.md` | §四 子模块划分、§五 子模块协作 | 子模块间依赖关系/调用链/数据流 |
| 各功能域 design.md（如 2_alloc/assign_design.md） | 细粒度子模块清单 | 同上 |

**禁止**：

- **禁止跳过反向刷新**：子模块验证后不刷新上层级 → 上层级文档与子模块不一致 → CK10 FAIL
- **禁止用上层级文档覆盖子模块验证结论**：子模块 Level 3-4 验证优先级高于上层 Level 1 概述
- **禁止只修正不标注来源**：每处修正必须标注来自哪个子模块 design.md 的哪个版本
- **禁止遗漏修正**：子模块 changelog 中标注的每个修正项（v{N}/v{N+1}）都必须检查上层级是否需要同步

**与前序步骤的关系**：

```text

CK1-CK8: 正向生成（顶层 → 子模块 design.md）
CK9: 增量分析（代码变更 → 受影响文档）
CK10: 反向刷新（子模块验证结论 → 修正上层级文档）  ← 本步骤

```

> **典型场景**：用户请求"生成某功能域子模块 md"，主 agent 先生成该功能域的 design.md（Level 1），再逐个生成子模块 design.md 并做 Level 2-4 深度验证。验证中发现某子模块数据结构描述有误（用链表不是红黑树）。CK10 要求回到功能域 design.md 修正同样的错误，确保上下层级一致。

## 质量约束

- **行数下限**: 读 knowledge.md §7 获取
- **Mermaid**: ≥3个（协作架构flowchart + 申请时序sequenceDiagram + 依赖flowchart）

- **源码验证声明**: 文档元信息必须包含"已验证文件列表"和"源码验证声明"

### 参考文档使用原则（CRITICAL）

> **参考文档是辅助理解，源码是唯一验证标准。** 参考文档用于理解模块功能/架构/算法概述；函数名/行号/结构体定义/文件路径必须从源码 Grep/Read 确认。违反 → CK8_CHECK FAIL。
