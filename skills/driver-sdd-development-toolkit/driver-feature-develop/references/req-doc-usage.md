## 各文档的核心价值

### spec.md（84 API 域索引）

**需求分析中的核心价值**：快速判断"是否有可复用的已有 API"

- §2 功能域表 → 按域查找 → 域目录路径 → 浏览 `{API}_spec.md` 文件列表
- 如果找到相似 API → 可以复用或扩展，不需要从零开始
- 如果没找到 → 需要新增 API

### 接口规格文档（`{domain}/{API}_spec.md`，每接口一个文件）

**需求分析中的核心价值**：获得已有 API 的完整调用链和约束条件

- 调用路径 → 画新需求的流程图时可以参考已有调用链
- 约束矩阵 → 确认新需求的参数约束是否与已有约束冲突
- 注意事项 → 理解设计限制
- 函数原型 → 参考接口签名格式

### 子模块文档（~50 个，7 节结构）

**需求分析中的核心价值**：理解设计意图和依赖关系

- §6 设计要点 → 理解子模块的设计决策，确认新需求是否与设计冲突
- §3.1 依赖 → 确认新代码依赖哪些下层模块
- §3.2 被依赖 → 确认哪些上层模块会调用新代码
- §5 关键结构体 → 确认可复用的结构体（handle_mng/handle/priv/svm_global_va）
- §2 对外接口 → 确认可复用的内部接口

### design.md（模块设计）

**需求分析中的核心价值**：确认新代码放在哪一层

- §4.1 分层架构 → 新代码放在哪个层，依赖哪些下层
- §5 子模块清单 → 新代码放在哪个子模块
- §4.2 关键结构体 → handle_mng→handle→priv 串联逻辑
- §2.1 目录结构 → 新代码放哪个目录（含强制约定）
- §1.3 对周边模块依赖 → 确认依赖链
- §3 对外接口 → 84 个 API 的域概览表

### 驱动级 AGENTS.md（约束规范）

**需求分析中的核心价值**：确认约束边界，避免违规

- §1 系统部署 → 确认用户态/内核态交互方式
- §2 对外接口契约 → 确认只新增不删除不修改（§2.3 兼容性规则）
- §3 编码规范 → 确认错误处理（§3.1）/日志格式（§3.2）/资源清理（§3.3）/消息结构体（§3.4）
- §4 禁区 → 确认不触及禁区（§4.1 绝对不能修改）/改动前人工确认（§4.3）
